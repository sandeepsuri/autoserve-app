AutoServe vendor scheduling

Availability setup that turns open-ended bookings into controlled vendor capacity.

This static prototype adds a first-run onboarding step and a live vendor availability editor behind the existing Adjust availability action in the bookings tab.

/(vendor)/availability + onboarding step

Current Design Read

  • The docs design board uses a mobile-first, card-based system with deep navy emphasis panels, blue operational CTAs, orange conversion CTAs, compact chips, and sticky phone previews.
  • Vendor screens are tab-first and operational: status filters, queue summaries, direct actions, and persistent bottom controls.
  • The booking schedule currently presents date and time chips without showing the source of truth for vendor working hours, blocked time, or service-specific slot limits.

Design Goals

1Make availability a required vendor onboarding step before the shop can receive bookings.
7Expose a week-level editor that maps directly to client-facing date chips.
15mLet vendors choose slot increments that constrain customer time selection.
0Prevent clients from selecting closed days, blocked time, or over-capacity slots.

Proposed Flow

01OnboardingAdd Availability after services, before review.
02Weekly RulesSet working days, hours, breaks, slot length, and capacity.
03ExceptionsBlock holidays, lunch, errands, or fully booked periods.
04Booking FeedAdjust availability opens this editor from vendor bookings.

Component States

  • Day chips support open, selected, closed, and fully booked states.
  • Slot cards support available, selected, blocked, booked, and disabled states.
  • Save actions include enabled, disabled, saving, success, and validation error states.
  • Client booking date chips should only render dates generated by published vendor rules.

Later adjustment state

When the vendor returns later, Adjust availability opens as an operations sheet.

The vendor starts from the bookings tab, sees the current workload, taps Adjust availability, and gets a focused editor for near-term changes without losing queue context.

What Changes After Onboarding

  • The step-progress onboarding card is replaced by a bookings workload summary and existing queue cards.
  • The editor opens as a bottom sheet over the bookings tab so vendors understand which bookings may be affected.
  • Near-term calendar chips become the primary control because later adjustments are usually exceptions, closures, or added capacity.
  • Conflict warnings appear before save when edits would hide slots that customers have already requested or booked.

Adjustment Behavior

TapBookings bottom action opens the availability sheet.
EditChange a day, block time, add emergency capacity, or pause same-day booking.
WarnOrange warnings show affected bookings and client-facing slot changes.
SaveChanges publish to client booking only after confirmation.

Resulting Client Experience

If the vendor blocks Friday afternoon, those time chips disappear from the client schedule step. If all slots on a day are removed, the date chip becomes unavailable and the client sees the next available CTA.
